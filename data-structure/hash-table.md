# 해시 테이블

> 날짜: 2026-11-11

## 무엇인가

키로 값을 바로 찾는 자료구조. 키를 **해시 함수**에 넣어 숫자로 바꾸고, 그 숫자로 배열의 몇 번 칸(버킷)에 넣을지 정한다. 찾을 때도 같은 계산을 하니까 처음부터 훑지 않고 그 칸으로 바로 간다. 그래서 평균 **O(1)**이다.

```
"KOPIS-123" → hash() → 98234 → 98234 % 16 = 10 → 10번 칸
```

### 용어 구분

| 용어 | 정체 | 하는 일 |
|---|---|---|
| 해시 (해시 함수) | 함수. 자료구조가 아니다 | 어떤 값을 정해진 범위의 숫자로 바꾼다 |
| 해시 테이블 | 자료구조 | 해시 함수 결과를 배열 칸 번호로 써서 저장한다 |
| Map | 추상 자료형 (Java에서는 인터페이스) | "키로 넣고 꺼낸다"는 기능만 정한다. 어떻게 저장할지는 안 정한다 |

```java
Map<String, Event> a = new HashMap<>();  // 해시 테이블로 구현 → 평균 O(1), 순서 없음
Map<String, Event> b = new TreeMap<>();  // 트리로 구현 → O(log n), 키 순서로 정렬
```

"Map이 해시 테이블"이 아니라 **"HashMap이 해시 테이블로 Map을 구현한 것"**이다.

## 왜 필요한가

리스트에서 값을 찾으려면 처음부터 하나씩 비교해야 한다(O(n)). 찾는 일을 여러 번 하면 비용이 곱해진다.

크롤링 항목 n건마다 기존 행사 m건 중 같은 것을 찾는다면

- **List로 찾기**: 항목마다 m건을 훑는다 → **O(n × m)**
- **HashMap으로 찾기**: m건을 Map에 한 번 넣고(O(m)), 항목마다 바로 찾는다(O(n)) → **O(n + m)**

n, m이 1,000이면 100만 번과 2,000번 차이다.

## 어떻게 동작하는가

### 해시 함수가 지켜야 할 것

- **같은 입력 → 항상 같은 결과.** 안 그러면 넣은 칸과 찾는 칸이 달라진다.
- **골고루 퍼뜨리기.** 한 칸에 몰리면 느려진다.
- 입력 길이는 제각각이어도 결과는 정해진 범위의 숫자다(Java `hashCode()`는 int 범위). 그래서 **다른 입력이 같은 결과가 될 수 있다(충돌).**

### 해시 충돌 처리

| | 체이닝 | 개방 주소법 |
|---|---|---|
| 방법 | 한 칸에 리스트로 이어 붙인다 | 칸이 차 있으면 정해진 규칙으로 다른 빈 칸을 찾는다 |
| 꽉 찰수록 | 리스트가 길어질 뿐 완만하게 느려진다 | 빈 칸 찾기가 급격히 오래 걸린다 |
| 삭제 | 리스트에서 빼면 끝 | 그냥 비우면 뒤 칸을 못 찾아서 "삭제됨" 표시가 필요하다 |
| 쓰는 곳 | Java `HashMap` | Java `IdentityHashMap`, `ThreadLocalMap`, fastutil 같은 외부 라이브러리 |

`HashMap`은 체이닝으로 고정이라 설정으로 바꿀 수 없다. 개방 주소법이 필요하면 다른 구현을 고른다.

### Java HashMap이 알아서 하는 것

- 충돌하면 한 칸에 **연결 리스트**로 이어 붙인다.
- 한 칸에 8개가 넘으면 **트리(레드-블랙 트리)**로 바꾼다(Java 8부터). 칸 안에서 찾는 비용이 O(k)에서 O(log k)로 준다.
- 전체의 75%가 차면(**load factor 0.75**) 배열을 2배로 늘리고 다시 나눠 담는다(리해싱).

### 개발자가 책임질 것

1. **`equals`와 `hashCode`를 같은 필드 기준으로 같이 재정의한다.** `hashCode`는 칸을 찾고, `equals`는 칸 안에서 진짜 같은 키인지 확인한다.
   - equals가 true면 hashCode는 반드시 같아야 한다.
   - hashCode가 같다고 equals가 true인 건 아니다. 이게 충돌이다.
2. **키로 쓴 객체의 값을 바꾸지 않는다.** 넣은 뒤 hashCode 계산에 쓰는 필드가 바뀌면 다른 칸을 보게 돼서 못 찾는다. 키는 불변 객체(`String`, `Long`, 값 객체)가 안전하다.
3. **크기를 알면 처음부터 넉넉히 만든다.** 늘릴 때마다 전부 다시 나눠 담기 때문이다.

### 대용량에서 나눠 세고 합치기

라이브 코테 P01(최다 조회 공고) 꼬리질문: "조회 로그가 하루 1억 건이면?"

HashMap 크기는 공고 수만큼이라 문제가 아니다. 문제는 1억 건을 매번 처음부터 읽는 것이다. 시간대·서버별로 나눠 세고 결과(Map)만 합친다.

```
[서버1, 10시] → {101: 500, 102: 30}
[서버2, 10시] → {101: 420, 103: 90}
[서버1, 11시] → {101: 610, 102: 55}
         ↓ 합치기
  {101: 1530, 102: 85, 103: 90}
```

```java
Map<Long, Long> total = new HashMap<>();
for (Map<Long, Long> part : parts) {
  part.forEach((postId, c) -> total.merge(postId, c, Long::sum));
}
```

- 세는 작업은 여러 서버가 동시에 할 수 있다.
- 합칠 때는 1억 건이 아니라 조각별 키 개수만큼만 돈다.
- 지난 결과에 새 조각만 더하면 된다.

**더할 수 없는 값은 다르다.** "중복을 뺀 조회자 수"는 10시 300명 + 11시 200명 = 500명이라고 할 수 없다. 두 시간대에 같은 사람이 있을 수 있다. 조각에 사용자 id를 **Set**으로 담고 합집합을 구해야 한다.

```java
Map<Long, Set<Long>> viewers = new HashMap<>();
viewers.computeIfAbsent(postId, k -> new HashSet<>()).add(userId);

total.merge(postId, part, (a, b) -> { a.addAll(b); return a; });
int uniqueViewers = total.get(postId).size();
```

대신 본 사람 id를 전부 들고 있어야 해서 메모리가 커진다. 대규모에서는 근사치를 적은 메모리로 구하는 방법(Redis HyperLogLog)을 쓰기도 한다. → 캐시와 Redis 주제에서 이어서 본다.

## 직접 확인한 것

팀 프로젝트(덕모임) 코드

- `EventIngestService.ingest()`: 기존 행사를 `findByExternalIdIn`으로 한 번에 읽고, `Collectors.toMap`으로 `Map<String, Event>`(externalId → Event)를 만든다. 크롤링 항목마다 `existing.get(externalId)`로 찾는다. 지역 코드 → id도 `regionIdsByCode()`에서 같은 방식으로 Map에 담는다.
- `Capacity`, `MeetPoint`, `BirthYear` 같은 값 객체에 `@EqualsAndHashCode`가 붙어 있다. Lombok이 equals와 hashCode를 같은 필드 기준으로 각각 만들어 주고, setter가 없어 값이 안 바뀐다. HashMap 키나 HashSet에 넣어도 안전한 구조다.
- `Event` 같은 엔티티에는 재정의하지 않았다. 엔티티는 저장 전후로 id가 바뀌고 필드도 바뀌어서 hashCode가 달라질 수 있다.

## 헷갈렸던 점

- **해시가 자료구조인가?** 아니다. 해시는 함수, 해시 테이블이 자료구조, Map은 기능만 정한 인터페이스다.
- **`@EqualsAndHashCode`는 equals가 hashCode로 비교하게 만드는 것?** 아니다. 두 메서드를 각각 만들되 같은 필드 기준으로 만든다. equals는 필드 값을 직접 비교한다.
- **hashCode가 전부 `1`이면?** 모든 키가 한 칸에 몰려 리스트에서 찾는 것과 같아지고 O(n)이 된다. 8개가 넘으면 트리로 바뀌지만, 해시값이 같아서 키가 `Comparable`이어야 O(log n)이 되고 아니면 여전히 O(n)에 가깝다. 배열을 늘려도 전부 같은 칸이라 소용없다.
- **충돌 처리를 개발자가 알아야 하나?** 리스트, 트리 전환, 배열 늘리기는 HashMap이 한다. 개발자는 equals/hashCode 재정의, 키 불변, 초기 크기를 책임진다.
- **`merge`와 `getOrDefault` + `put`의 차이?** 한 스레드에선 결과가 같다. `merge`는 칸을 한 번만 찾는다. `ConcurrentHashMap`에서는 `merge`가 원자적이고 `get` + `put`은 아니라서, 동시에 +1 하면 갱신 손실이 생긴다. → 락 주제에서 이어서 본다.
- **중복 제거 조회자를 담을 때 List?** Set이어야 한다. List면 합칠 때 같은 사람이 두 번 들어간다.
- **크기 구하기:** 배열은 `arr.length`, 문자열은 `str.length()`, 컬렉션은 `size()`.
- **Big-O 말할 때 변수 이름을 먼저 정한다.** n, m이 무엇인지 섞이면 답이 틀려 보인다.

## 면접용 정리

> 해시 테이블은 키를 해시 함수로 숫자로 바꿔 배열 칸을 정하기 때문에 평균 O(1)에 값을 찾습니다. 덕모임 행사 적재에서는 기존 행사를 externalId를 키로 하는 HashMap에 담아 두고 크롤링 항목마다 바로 찾습니다. 리스트로 찾으면 O(n × m)이지만, Map을 한 번 만들어 두면 O(n + m)으로 처리됩니다.

> Java HashMap은 충돌을 체이닝으로 처리하고, 한 칸에 8개가 넘으면 트리로 바꿔 최악의 경우를 줄입니다. 그래서 키 객체는 equals와 hashCode를 같은 필드 기준으로 재정의하고 불변으로 두는 게 중요합니다. 덕모임의 정원, 만남 장소 같은 값 객체도 이 기준으로 되어 있습니다.
