# 인덱스

> 원하는 데이터를 빨리 찾도록, 컬럼 값을 정렬해 따로 저장해 둔 목록

## 무엇인가

- 책 맨 뒤의 '찾아보기(색인)'와 같다. 단어가 가나다순으로 정렬돼 있고, 옆에 몇 쪽인지 적혀 있다.
- DB 인덱스도 특정 컬럼 값을 정렬해 둔 별도의 목록이고, 각 값 옆에 실제 행을 찾아가는 주소가 있다. MySQL(InnoDB)에서는 그 주소가 행의 기본키다.
- 인덱스는 테이블과 별도의 공간에 저장된다. `SELECT`로 직접 조회하는 대상이 아니라, DB가 조회할 때 알아서 꺼내 쓰는 내부 자료다.

## 왜 필요한가

- 인덱스가 없으면 DB는 표를 처음부터 끝까지 다 읽는다 (풀 스캔).
- 인덱스가 있으면 정렬된 목록에서 원하는 값의 위치로 바로 찾아간다.
- 대신 공짜가 아니다. 글을 쓰거나 고칠 때마다 인덱스도 같이 갱신해야 해서, 인덱스가 많을수록
  - 조회는 빨라지고
  - 쓰기는 느려지고
  - 저장 공간이 더 든다.

## 어떻게 동작하는가

### 여러 컬럼 인덱스는 앞 컬럼부터 정렬된다

인덱스 `(status, meet_at, id)`는 `status`로 먼저 정렬하고, 같으면 `meet_at`, 그것도 같으면 `id`로 정렬한다.

전화번호부가 '성 → 이름' 순인 것과 같다.

- "김씨 중 민수" 찾기 → 김씨 구역으로 바로 간다 ✅
- "이름이 민수인 사람 전부" 찾기 → 성이 먼저 정렬돼 있어서 처음부터 다 봐야 한다 ❌

그래서 **앞 컬럼 조건이 있어야 그 인덱스를 순서대로 쓸 수 있다.**

예: `(status, meet_at)` 인덱스 안의 실제 순서

| 순서 | status | meet_at |
|---|---|---|
| 1 | CLOSED | 09:00 |
| 2 | CLOSED | 12:00 |
| 3 | OPEN | 10:00 |
| 4 | OPEN | 11:00 |

- `status = 'OPEN'`을 `meet_at` 순으로 → OPEN 구역에서 순서대로 읽으면 끝
- status 상관없이 `meet_at` 순으로 → 09:00, 12:00, 10:00, 11:00으로 순서가 끊겨서 다시 정렬해야 한다

### 앞부분이 같은 인덱스는 중복이다

`(status, meet_at, id)`가 있으면 `(status, meet_at)`이 하던 조회를 전부 대신할 수 있다. 남겨 두면 쓰기 비용만 든다.

### 인덱스는 쿼리에 직접 쓰지 않는다 (옵티마이저)

- 조회할 때 인덱스 이름을 쓰지 않는다. WHERE와 ORDER BY만 쓰면 DB가 알아서 맞는 인덱스를 고른다.
- 이걸 고르는 게 **옵티마이저**다. 길 찾기 앱처럼, 가능한 방법(인덱스 A, 인덱스 B, 풀 스캔)의 비용을 비교해 가장 싼 **실행 계획**을 고른다.
- 그래서 인덱스는 **쿼리의 WHERE와 ORDER BY 모양에 맞춰** 만든다.
- 인덱스가 있어도 안 쓸 때가 있다.
  - 데이터가 적어서 다 읽는 게 더 쌀 때
  - 조건에 걸리는 행이 너무 많을 때 (값 종류가 적은 컬럼, 카디널리티가 낮을 때)
- 옵티마이저는 DB 종류, 버전, 데이터 통계에 따라 판단이 달라진다. 로컬에서 데이터 몇 개로 본 결과와 운영 결과가 다를 수 있다.

### 어떤 인덱스를 썼는지 확인: EXPLAIN

```sql
EXPLAIN SELECT * FROM companion_post
WHERE status = 'OPEN'
ORDER BY meet_at, id
LIMIT 20;
```

- `key`: 실제로 쓴 인덱스. `NULL`이면 풀 스캔
- `Extra`에 `Using filesort`: 인덱스 순서를 못 써서 따로 정렬했다는 뜻

### 인덱스는 언제든 만들 수 있지만

`CREATE INDEX`로 나중에도 만들 수 있다. 다만 데이터가 많이 쌓인 운영 표에서는 표 전체를 읽어 새로 정렬해야 해서 시간과 부하가 크다. 조회 조건이 정해지는 시점, 데이터가 적을 때 함께 두는 게 가장 싸다.

## 직접 확인한 것

팀 프로젝트(덕모임) 모집글 표에서 내가 만든 인덱스 (Flyway 마이그레이션 V22)

```sql
CREATE INDEX ix_companion_post_status_meet_at_id ON companion_post (status, meet_at, id); -- 모집중만 보기
CREATE INDEX ix_companion_post_meet_at_id ON companion_post (meet_at, id);                -- 전체 보기
DROP INDEX ix_companion_post_status_meet_at ON companion_post;                            -- 중복이라 삭제
```

- 목록 조회가 '모집중만 보기'와 '전체 보기' 두 가지라 인덱스를 따로 만들었다.
- 전체 보기에는 `status` 조건이 없어서, `status`로 시작하는 인덱스로는 `meet_at` 순서를 유지할 수 없다.
- 기존 `(status, meet_at)`은 새 인덱스가 같은 역할을 해서 삭제했다.
- 같은 표에 다른 조회용 인덱스도 있다. '내가 쓴 글'은 `(host_id, created_at, id)`, 파기 배치는 `(status, closed_at)`. 조회마다 거르는 조건과 정렬이 달라서 인덱스도 따로 필요하다.

## 헷갈렸던 점

- **인덱스 = 책갈피?** 책갈피는 한 곳만 표시한다. 인덱스는 정렬된 목록 전체라서 '찾아보기'에 더 가깝다.
- **데이터가 적은데 왜 인덱스를 만들었나?** 당시엔 성능 차이가 거의 없었다. 조회 조건이 확정된 시점에, 나중에 큰 표에 추가하는 것보다 부담이 적어서 함께 넣었다. 측정한 적이 없으니 "성능을 개선했다"고 말하면 안 된다.
- **기존 인덱스를 왜 지웠나?** 처음엔 'OPEN 조회에 안 쓰여서'라고 생각했다. 실제 이유는 새 인덱스가 앞부분을 그대로 포함해 같은 역할을 하기 때문이다.
- **왜 인덱스를 둘로 나눴나?** 처음엔 status 값 종류가 적어서라고 생각했다 (이건 '카디널리티'라는 별도 개념). 실제 이유는 전체 보기에 status 조건이 없어서 앞 컬럼을 못 쓰기 때문이다.
- **조회할 때 인덱스를 어떻게 쓰나?** 쿼리에 직접 쓰는 게 아니라, 옵티마이저가 WHERE와 ORDER BY를 보고 고른다. 쓰는지는 EXPLAIN으로 확인한다.
- **아직 남은 질문:** 인덱스 끝에 `id`를 붙인 이유 → 페이지네이션에서 정리
