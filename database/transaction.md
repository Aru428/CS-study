# 트랜잭션과 격리 수준

> 날짜: 2026-11-13 (격리 수준 4가지는 다음에 이어서)

## 무엇인가

**트랜잭션**은 여러 DB 작업을 "전부 성공하거나, 전부 없던 일이 되는" 하나의 단위로 묶는 것. 중간에 하나라도 실패하면 앞에서 한 것까지 되돌리고(롤백), 끝까지 성공해야 확정(커밋)된다.

트랜잭션은 메서드가 아니라 **DB가 제공하는 작업 단위(개념)**다. 메서드는 그 단위의 시작과 끝을 정하는 곳이다.

```sql
START TRANSACTION;
UPDATE event SET title = '...' WHERE id = 1;
UPDATE event SET title = '...' WHERE id = 2;
COMMIT;   -- 실패하면 ROLLBACK
```

아무것도 안 묶으면 MySQL은 SQL 한 줄이 각자 트랜잭션이다(autocommit).

### ACID

- **원자성 (Atomicity)**: 전부 아니면 전무
- **일관성 (Consistency)**: 전후로 제약 조건(FK, UNIQUE 등)이 지켜진다
- **격리성 (Isolation)**: 동시에 도는 트랜잭션끼리 서로의 중간 상태를 얼마나 못 보게 할지
- **지속성 (Durability)**: 커밋된 건 서버가 죽어도 남는다

## 왜 필요한가

여러 행을 고치는 중간에 실패하면, 일부만 바뀐 어중간한 상태가 DB에 남는다. 크롤링 행사 100건 중 49건만 갱신되면 화면에는 반은 새 정보, 반은 옛날 정보가 섞인다.

## 어떻게 동작하는가

### 누가 무엇을 하나

| 누가 | 하는 일 |
|---|---|
| Spring (`@Transactional`) | 메서드 시작에 트랜잭션 시작, 끝날 때 커밋할지 롤백할지 **판단** |
| JPA (Hibernate) | 엔티티 관리, 변경 감지, SQL 생성, flush |
| DB (MySQL) | SQL 실행, 실제 COMMIT / ROLLBACK 수행 |

### `@Transactional`이 롤백하는 조건

판단 순서는 두 단계다.

1. **메서드 밖으로 나간 예외가 무엇인가?** 안에서 잡혀서 삼켜진 예외는 Spring이 모른다 → 커밋
2. **그 예외가 언체크인가 체크인가?**

| 예외 종류 | 예 | 기본 동작 |
|---|---|---|
| 언체크 (`RuntimeException` 상속) | `BusinessException`, `NullPointerException`, `IllegalArgumentException`, `IllegalStateException`, `DataAccessException` | 롤백 |
| `Error` | `OutOfMemoryError` | 롤백 |
| 체크 (`Exception` 상속, `RuntimeException` 가지 제외) | `IOException`, `SQLException`, `Exception` | **커밋** |

체크 예외도 롤백하려면

```java
@Transactional(rollbackFor = IOException.class)   // 방법 1: 지정

catch (IOException e) {                            // 방법 2: 언체크로 감싸 던지기
  throw new IllegalStateException("파일 읽기 실패", e);
}
```

catch 후 다시 던질 때는 **던지는 객체의 타입**이 기준이다. 안에 감싼 원인(cause)은 상관없다.

| 코드 | 밖으로 나가는 예외 | 결과 |
|---|---|---|
| 잡지 않음 | `BusinessException` | 롤백 |
| `catch` 후 `throw e;` | `BusinessException` | 롤백 |
| `catch` 후 `throw new RuntimeException(e);` | `RuntimeException` | 롤백 |
| `catch` 후 `throw new Exception(e);` | `Exception` | 커밋 |
| `catch` 후 로그만 | 없음 | 커밋 |

JPA를 쓰면 DB 오류는 Spring이 `DataAccessException`(언체크)으로 바꿔서 올려 주므로 기본으로 롤백된다.

### JPA가 SQL을 보내는 시점 (flush)

변경 감지로 바뀐 필드가 있는 엔티티만 UPDATE를 보낸다. 보내는 시점은

- 커밋할 때
- JPQL 쿼리를 실행하기 직전 (안 보내면 쿼리가 옛날 값으로 결과를 내니까)
- `flush()`를 직접 부를 때

id가 `IDENTITY` 방식인 엔티티는 DB가 id를 만들어 줘야 해서 `save()` 시점에 INSERT가 바로 나간다.

### 커밋 전 값은 DB 어디에 있나

UPDATE를 보내면 DB는 그 행을 **바로 바꾼다.** 커밋은 값을 쓰는 게 아니라 이미 쓴 걸 확정하는 것이다. InnoDB는 바꾸기 전 값을 **언두 로그(undo log)**에 백업해 두고, 롤백하면 그걸로 되돌린다.

```
테이블의 행 1:  "콘서트(수정)"   ← 새 값 (커밋 전)
언두 로그:       "콘서트"         ← 옛날 값
```

다른 트랜잭션이 읽을 때 지금 행을 보여 줄지, 커밋된 옛날 버전을 보여 줄지를 정하는 게 격리 수준이다. 한 행의 여러 버전을 두고 골라 보여 주는 방식을 MVCC라고 한다.

### 격리성: 왜 단계가 필요한가

완벽하게 격리하려면 트랜잭션을 한 번에 하나씩 줄 세우면 된다. 하지만 10초짜리 적재가 돌면 0.01초짜리 조회 100개가 전부 기다린다. 서로 상관없는 데이터를 건드리는 요청까지 기다리게 된다.

그래서 동시에 돌리되, 같은 데이터를 건드릴 때 어디까지 보여 줘도 되는지를 단계로 고르게 한 것이 **격리 수준**이다.

### 동시에 돌 때 생기는 문제 3가지

| 문제 | 읽은 값 | 원인 | 대상 |
|---|---|---|---|
| 더티 리드 | 커밋 **전** 값 | 다른 트랜잭션의 미확정 수정 | 한 행의 값 |
| 반복 불가능한 읽기 | 커밋**된** 값 | 내 트랜잭션 중간에 다른 트랜잭션이 **수정 후 커밋** | 한 행의 값 |
| 팬텀 리드 | 커밋**된** 값 | 내 트랜잭션 중간에 다른 트랜잭션이 **추가/삭제 후 커밋** | 조건에 맞는 여러 행의 개수 |

판단 순서

1. 커밋 전 값을 읽었나? → 더티 리드
2. 커밋된 수정으로 한 행의 값이 바뀌었나? → 반복 불가능한 읽기
3. 커밋된 추가/삭제로 행 개수가 바뀌었나? → 팬텀 리드

**더티 리드는 결국 커밋돼도 문제다.** 읽는 순간엔 커밋될지 모르고, 100건을 한 트랜잭션으로 고치는 중이면 반만 바뀐 목록이 보일 수 있다. 한 번도 존재하지 않아야 할 상태를 본 것이다.

**반복 불가능한 읽기, 팬텀 리드가 문제인 이유**: 트랜잭션 하나는 한 시점의 일관된 데이터를 기준으로 일하길 기대한다. 두 번 읽은 게 서로 다른 트랜잭션이라면 새 값이 보이는 건 정상이다.

### 다음에 볼 것: 격리 수준 4가지

READ UNCOMMITTED, READ COMMITTED, REPEATABLE READ(MySQL 기본), SERIALIZABLE. 각각 위 문제 중 어디까지 막는지, MySQL REPEATABLE READ가 MVCC로 팬텀 리드를 어떻게 대부분 막는지.

## 직접 확인한 것

팀 프로젝트(덕모임) `EventIngestService.ingest()`

- 메서드에 `@Transactional`. 주석: "트랜잭션 하나다. 절반만 들어가고 죽으면 DB가 어중간한 상태로 남는다." 지금은 직전 커밋의 `events.json`이 안전망이지만 전환 후에는 그 안전망이 없다는 이유.
- 크롤링 항목마다 기존 행사는 `event.syncFrom(...)`으로 필드만 바꾼다(save 호출 없음, 변경 감지). 새 행사는 모아서 `saveAll`.
- `regionIdOf`: 없는 지역 코드를 기본 구역으로 넣지 않고 `BusinessException`을 던진다. 조용히 넣으면 지도 핀이 엉뚱한 곳에 서고 크롤러 오타를 알 방법이 없어진다는 이유.
- `BusinessException extends RuntimeException` → 언체크라 롤백된다.
- 순서: `syncFrom`(SQL 안 나감) → `saveAll`(`Event` id가 `IDENTITY`라 INSERT 바로 나감) → `report()`의 `countStale` JPQL 직전 flush로 UPDATE 나감 → 커밋. 그래서 INSERT 이후 ~ 커밋 사이에는 커밋 안 된 변경이 DB에 실제로 있다.

## 헷갈렸던 점

- **트랜잭션은 메서드인가, DB인가?** DB가 제공하는 작업 단위다. `@Transactional`은 메서드의 시작과 끝을 그 단위의 경계로 쓰겠다는 표시다.
- **롤백은 내가 한 게 아니라 어노테이션이 한 것 아닌가?** 맞다. 개발자가 한 건 판단이다. 어디까지 한 묶음으로 할지(배치 전체 vs 항목별), 잘못된 값을 조용히 넘기지 않고 예외를 낼지, 롤백되는 예외를 쓸지. 배치 전체로 묶으면 1건만 틀려도 전부 실패하는 비용을 받아들인 것이다.
- **체크 / 언체크를 반대로 알고 있었다.** `IOException`, `SQLException`이 체크, `RuntimeException` 가지가 언체크. "Runtime이 붙으면 언체크".
- **체크 / 언체크는 트랜잭션 기준인가?** 아니다. Java 언어 자체의 구분이다. 체크는 "컴파일러가 처리했는지 검사한다"는 뜻. Spring은 그 분류를 가져다 롤백 기본값을 정했을 뿐이다.
- **체크 / 언체크는 catch문 유무로 정해지나?** 아니다. 예외 클래스가 `RuntimeException`을 상속했는지로 정해진다. catch는 체크 예외를 처리하는 방법 중 하나다.
- **체크 예외는 메서드 안에서 꼭 처리해야 하나?** catch로 처리하거나 `throws`로 위에 넘기거나 둘 중 하나. 넘기면 부른 쪽이 같은 선택을 해야 하고, 결국 호출 경로 어딘가에서 처리해야 한다.
- **`throw new Exception(e)`가 체크인 이유가 e 때문?** 아니다. e는 `BusinessException`이다. 던지는 객체가 `Exception` 타입이라 체크다.
- **커밋 판단은 JPA가 하나?** Spring이 한다. JPA는 SQL을 만들고 보낸다.
- **커밋 전이면 DB에 값이 없을 텐데 어떻게 더티 리드가 되나?** UPDATE를 보내면 DB 행은 바로 바뀌고 옛날 값은 언두 로그에 있다. JPA flush 전이라면 DB에 정말 없다.
- **JPA는 커밋 직전에 무조건 UPDATE를 보내나?** 바뀐 게 있을 때만, 그리고 커밋 때뿐 아니라 JPQL 실행 직전에도 보낸다.
- **반복 불가능한 읽기는 격리 수준인가?** 아니다. 문제(현상)다. 격리 수준은 READ UNCOMMITTED 등 4가지.
- **반복 불가능한 읽기 예시는 하나의 트랜잭션인가?** B의 두 번 읽기가 B 트랜잭션 하나, A는 따로 도는 트랜잭션이다.
- **완벽한 격리가 왜 느린가?** 한 번에 하나씩 줄 세우면 상관없는 데이터를 건드리는 요청까지 앞의 긴 작업을 기다린다.

## 면접용 정리

> 트랜잭션은 여러 DB 작업을 전부 성공하거나 전부 취소되는 하나의 단위로 묶는 것으로, 원자성, 일관성, 격리성, 지속성을 보장합니다. 덕모임 행사 적재는 크롤링 배치 하나를 한 트랜잭션으로 묶어서, 한 건이라도 잘못되면 배치 전체를 되돌리고 일부만 들어간 상태가 남지 않게 되어 있습니다. 그래서 없는 지역 코드도 기본값으로 넘기지 않고 예외를 냅니다.

> `@Transactional`은 메서드 밖으로 나간 예외가 언체크 예외일 때만 기본으로 롤백하고, IOException 같은 체크 예외는 커밋합니다. 체크 예외도 롤백해야 하면 rollbackFor로 지정하거나 언체크 예외로 감싸서 던집니다. 예외를 안에서 잡고 다시 던지지 않으면 정상 종료로 보고 커밋되니 주의해야 합니다.

> 트랜잭션이 동시에 돌면 커밋 전 값을 읽는 더티 리드, 한 트랜잭션 안에서 다른 트랜잭션의 커밋된 수정으로 같은 행의 값이 바뀌는 반복 불가능한 읽기, 추가나 삭제로 같은 조건의 행 수가 바뀌는 팬텀 리드가 생길 수 있습니다. 격리 수준은 이 중 어디까지 막을지 고르는 설정입니다.
