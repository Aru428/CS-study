# 페이지네이션 (오프셋, 커서)

> 날짜: 2026-11-10

## 무엇인가

데이터를 한 번에 다 주지 않고, 정해진 개수만큼 나눠서 주는 것.

화면에서는 두 가지 모양으로 보인다.

- **페이지 번호형**: 게시판 아래 `1 2 3 4 5 >`. 원하는 페이지로 바로 간다.
- **무한 스크롤형**: 아래로 내리면 다음 글이 계속 붙는다. 덕모임 모집글 목록이 이 형태다.

## 왜 필요한가

모집글이 1만 개일 때 목록을 열 때마다 전부 보내면

- **DB**는 1만 개를 읽느라 느려진다. 다른 요청과 같이 쓰는 자원이라 다른 API까지 느려진다.
- **서버**는 1만 개를 객체로 만들고 JSON으로 바꾸느라 메모리를 많이 쓴다.
- **사용자**는 목록을 늦게 받고 데이터도 많이 쓴다. 정작 보는 건 위쪽 20개 정도다.

실제로 보는 건 일부라서, 필요한 만큼만 나눠 준다.

## 어떻게 동작하는가

### 오프셋 방식: 앞에서부터 몇 개를 건너뛰기

```sql
-- 3페이지 (페이지당 20개)
SELECT * FROM companion_post ORDER BY meet_at, id
LIMIT 20 OFFSET 40;
```

"41번째 줄부터 읽어"처럼 줄 수를 센다. 페이지 번호형에 잘 맞는다. 3페이지는 40개 건너뛰기로 바로 계산된다.

문제는 두 가지다.

- **뒤로 갈수록 느려진다.** DB가 앞의 40개를 실제로 읽고 버린다. 1000페이지면 2만 개를 읽고 버린다.
- **목록이 바뀌면 중복이나 누락이 생긴다.**
  - 앞쪽에 글이 하나 생기면 모두 한 칸씩 밀려서, 다음 페이지에 이미 본 글이 또 나온다 (중복).
  - 앞쪽 글이 하나 빠지면 모두 한 칸씩 당겨져서, 못 본 글을 건너뛴다 (누락).

### 커서 방식: 마지막으로 본 글 다음부터

```sql
SELECT * FROM companion_post
WHERE (meet_at > :cursorMeetAt
       OR (meet_at = :cursorMeetAt AND id > :cursorId))
ORDER BY meet_at, id
LIMIT 20;
```

책갈피를 꽂아 두고 거기서부터 읽는 방식이다.

- 인덱스로 책갈피 위치에 바로 가서 읽으니 몇 번째 페이지든 속도가 같다.
- 앞쪽에 글이 생기거나 빠져도 기준(마지막으로 본 글)은 그대로라 중복이나 누락이 없다.
- 대신 "5페이지로 바로 가기"는 못 한다. 무한 스크롤에는 필요 없는 기능이다.

### 커서 키에 id를 같이 넣는 이유

정렬 기준 값(meet_at)은 겹칠 수 있다. 한 페이지 2개, 이런 데이터가 있다고 하자.

| id | meet_at |
|---|---|
| 7 | 11/15 14:00 |
| 3 | 11/15 18:00 |
| 5 | 11/15 18:00 |
| 9 | 11/16 12:00 |

1페이지에서 id 7, 3을 받았다. 마지막 meet_at은 18:00.

| 다음 페이지 조건 | 결과 | 문제 |
|---|---|---|
| `meet_at > 18:00` | 9 | id 5 **누락** |
| `meet_at >= 18:00` | 3, 5, 9 | id 3 **중복** |
| `meet_at > 18:00 OR (meet_at = 18:00 AND id > 3)` | 5, 9 | 없음 |

id는 겹치지 않는 값이라, 시각이 같은 글끼리도 순서가 하나로 정해진다. 그래서 **커서 키는 정렬 키와 같아야 하고, 마지막에 겹치지 않는 값(id)이 들어가야 한다.**

### 인덱스와의 연결

정렬과 커서 조건이 `meet_at, id` 순서라서, 인덱스도 같은 순서로 만들어야 책갈피 위치로 바로 갈 수 있다. 인덱스 정리에서 남겨 둔 질문("인덱스 끝에 id를 붙인 이유")의 답이 이것이다.

## 직접 확인한 것

팀 프로젝트(덕모임) 모집글 목록 코드

- `CompanionPostQueryRepositoryImpl`: 커서 조건 `(p.meetAt > :cursorMeetAt OR (p.meetAt = :cursorMeetAt AND p.id > :cursorId))`, 정렬 `ORDER BY p.meetAt ASC, p.id ASC`
- `PostCursor(meetAt, id)`: 둘 중 하나라도 없으면 예외. 코드 주석에도 "커서 키는 정렬 키와 같아야 한다", "meetAt은 중복이 생긴다"가 적혀 있다.
- 인덱스: V22 `(status, meet_at, id)`, `(meet_at, id)`
- '내가 쓴 글' 목록은 정렬이 작성 최신순이라 커서도 `(createdAt, id)`다. 정렬이 다르면 커서와 인덱스도 따로 필요하다.

모집글 목록에 커서를 쓴 이유

- 목록이 만남 시각 순이라 새 글이 중간에 끼어들고, 만남 시각이 지난 글은 배치가 마감해 빠진다. 오프셋이면 이때 중복이나 누락이 생긴다.
- 화면이 무한 스크롤이라 페이지 이동이 필요 없다.

## 헷갈렸던 점

- **페이지네이션이 없으면 누가 손해인가?** 처음엔 서버라고 생각했다. 실제로는 DB(많이 읽음), 서버(많이 변환), 사용자(늦게 받음) 모두 손해다.
- **커서를 쓴 이유는 무한 스크롤이라서?** 반만 맞다. 무한 스크롤이라 커서의 단점(페이지 이동 불가)이 문제가 안 되는 것이고, 핵심은 목록이 계속 바뀌어서 오프셋이면 중복이나 누락이 생긴다는 점이다.
- **새 글이 생기면 중복, 누락은 언제?** 새 글이 끼어들면 밀려서 중복, 글이 빠지면 당겨져서 누락.

## 면접용 정리

> 모집글 목록은 새 글이 중간에 생기거나 마감된 글이 빠지면서 계속 바뀌기 때문에, 오프셋 방식이면 중복이나 누락이 생길 수 있었습니다. 화면도 페이지 이동이 필요 없는 무한 스크롤이라 커서 방식을 썼습니다. 만남 시각은 겹칠 수 있어서 겹치지 않는 id를 커서에 함께 넣었고, 인덱스도 같은 순서로 만들었습니다.
